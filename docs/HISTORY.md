# History

How the model and its published numbers got to where they are. The current model is described in
[SIM_SPEC.md](../SIM_SPEC.md), its rules in [RULES.md](../RULES.md), the website in [README.md](../README.md).

Scope of every number: April–June 2026, 79 plan dates, 6,501 tables, unless a line says otherwise. Fleet
figures use the 7-day round trip, an **ESTIMATE** that has never been timed.

What each step shows:
- **(0) → (i), the pairs rule.** S0 does not move (it ignores the option). S3 falls 69.77 → 68.13% and
  needs 24 more trolleys. The script does not isolate why.
- **(i) → (ii), changeover and moving.** Cut end times move, and the loading order and the WIP hold follow
  them. S0 cutter output falls (80,107 → 75,594 a day): lost time can only cost output.
- **(ii) → (iii), no speed factor.** Machines run faster, so output and S0 utilization rise.
- **(iii) → (iv), the real Job Sequence.** Only S0 and the 39 `today` sweep keys move (asserted). The SQL
  balances spreaders by spreading minutes, not by their shift minutes (quirk Q21), so the cutters wait and
  S0 output falls to 72,593 a day. S0 → S1 is now two changes: a different dispatcher and pairing.
- **(iv) → (v), the live floor.** Every number moves. Tables now wait for their marker and fabric, so the
  backlog the floor of 2026-11-09 built is gone (650,964 → 48,757 pieces uncut on the real plan), and the
  three rules no longer change cutter output (all within 0.5%). S2 loses most (64.67 → 61.17%).
- **(v) → (vi), Q1 fixed.** S0–S3 and the five hold variants are bit-identical (asserted). Only the 36 sweep
  keys with 1 batch and a hold move, all downward, because they had been mixing two batches:

| today \| 1 \| 240 \| any | 73.26 → 63.92 | 144.2 → 165.3 |

hold (`cross_batch | 2 | 240 | any`) is 73.87%: the old 1-batch figure was a 2-batch result.

**Asserts** (`npm run beforeafter` exits non-zero if any fails): stage (0) equals the 2026-11-06 headline;
stage (iii) the 2026-11-09 headline; stage (iv) the 2026-11-10 headline; S1–S3, the hold variants and the 78
non-`today` sweep keys are bit-identical from (iii) to (iv); S0–S3 and the hold variants are bit-identical

**Rule (a), two ways.** Case 1 = pairs over the floor (published); case 2 = keep an MO on one cut group (the

1,062 (case 1) against 66.85% / 153.1 / 1,072 (case 2); cutter output differs by under 1%. Which to keep is the user's decision; the model keeps
case 1.

## Decisions taken

| Date | Decision |
|---|---|
| 2026-11-16 | Cutter count and table length are not page controls; the engine keeps them for other factories. |
| 2026-11-14 | 2 batches per trolley only under Cross-batch; 1 batch never mixes (Q1). |
| 2026-11-13 | Node only; no Python copy. |
| 2026-11-10 | The floor is live (re-plan every 30 min, readiness, the longest-wait cutter pick). S0 is the real Job Sequence, core loop only, mirrored as written; priority by order type is an ESTIMATE. |
| 2026-11-10 | No dynamic spreader pick; no "keep same colour close". |
| 2026-11-09 | No cold start, ever. No machine speed factor. Cutter changeover 5 min and moving 1.5 min are part of the floor (ESTIMATES); spreaders get no extra changeover or moving. The cutter always moves between spreaders. |
| 2026-11-09 | Rule (a): pair first, count by pairs, assign over the floor. "Keep an MO on one cut group" is an option, not rule (a). |
| 2026-11-09 | S2 and S3 stay in the published table as reference scenarios rather than as a rule to adopt. |
| 2026-11-06 | Carry-over: work is always left from the day before. The requirement is 100,000 pieces a day. |
| 2026-09-08 | The website shows April–June only; the gates and measurement scripts read the full file. |
